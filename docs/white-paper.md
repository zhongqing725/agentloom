# 织序 AgentLoom

## 可验证的多 Agent 团队编排与调度平台

**2026 第五届“未来杯”创新大赛（校赛）· 赛题一（Agent 编排创新应用）**

项目白皮书 · v0.1

---

## 摘要

多 Agent 系统正在从演示走向生产，但真正落地时普遍遇到三道坎：团队结构写死、思考过程黑盒、结果无法验证。织序 AgentLoom 把“团队”拆成一张可编排的图，把“思考”做成可挂载的节点能力插件，把“结果”交给核查器与 Self-Loop。

平台的差异化不在于“支持多少个 Agent”，而在于三个可演示的动作：

1. 把一张“发散思考”插件挂到任意 Agent 节点上，该节点展开稳健、进取、反方三条思维分支；
2. 裁判按证据覆盖、假设可检验性、行动性收敛出一个主判断；
3. 核查员逐条核对结论与证据，按问题类型把问题路由回对应的上游节点，而不是一律重写。

工具不是另起一套系统：`calculator` 与 `knowledge_search` 通过同一张工具注册表执行，Live 模式走 function calling，Mock 模式也留下真实的 `tool.call` 轨迹。

我们以“AI 眼镜产业链投研”为首发场景，跑通了知识库、8 角色默认团队（团队库 14 个角色）、三路并行研究、节点级发散、工具计算、裁判收敛、四态核查与 Self-Loop 的完整闭环。内测运行中，报告第一轮核查 86%，发现 3 条问题：数字矛盾被路由回首席分析师，缺引用被路由回竞争情报员；第二轮达到 100%。四态核查在 42 条手标难例上准确率 88%，`supported` F1 100%。

## 一、项目概述

### 1.1 背景：多 Agent 的三道坎

**第一道坎：团队写死。**
多数 Agent 产品把角色、工具、流程硬编码在代码或提示词里。用户想加一个“风险审查员”，往往要改代码；想换一个行业，往往要重做一套系统。

**第二道坎：思考黑盒。**
“让模型多想几步”通常只是一句提示词。用户不知道它想了哪几个角度、每个角度质量如何、为什么最后选了这个结论。

**第三道坎：结果不可验。**
Agent 说“报告完成了”，但报告里的数字是否有依据、引用是否真的支持结论、哪些地方是假设，缺少可复现的核查。失败之后，系统通常只是重试，而不是带着问题修正。

这三道坎决定了：多 Agent 的门槛不在“能不能跑”，而在“能不能被控制、被解释、被验收”。

### 1.2 项目定位

织序 AgentLoom 是一个**验证优先的多 Agent 编排调度平台**：

> Agent 是主机，插件是卡，画布是工作台。

- **团队层**：默认 8 个角色组成 DAG（团队库 14 个），支持并行、依赖、回环。
- **认知层**：节点可以挂载能力插件，改变“这个节点怎么想”。
- **验证层**：核查器把结论与证据对齐，失败驱动回写。
- **观察层**：调度、分支、回环、Token 全部事件化，可实时看、可回放。

### 1.3 应用范围

平台本身不绑定行业。首发场景选择“产业投研”，因为该场景同时具备三个特征：

- 资料密集，需要知识库与引用；
- 结论开放，需要多视角与裁判；
- 错误代价高，需要事实核查。

可迁移的场景包括：企业战略研究、政策研究、竞品分析、软件交付、客服工单、招投标文件编制等。迁移时替换的是 Agent 角色、知识源与提示词，插件与运行时保持不变。

### 1.4 核心优势

1. **节点级能力插件**：不是“换一个 Agent”，而是“给同一个 Agent 换一种思考方式”。
2. **验证驱动回环**：核查结果不是展示分数，而是下一轮写作的输入。
3. **可观察的调度**：优先级、并发、重试、回环都以事件呈现，能解释“为什么先跑这个”。
4. **知识库 grounding**：结论带稳定引用，引用可回到原文。
5. **可演示的闭环**：拖卡、展开、裁判、核查、回环，3 分钟能讲清楚。

## 二、解决方案

### 2.1 总体架构

| 层 | 组成 | 职责 |
|---|---|---|
| 控制台 | React 19、Vite、React Flow | 首页、知识库、团队、画布、运行、评测、训练 |
| API | Fastify、REST、SSE | 运行、知识库、Agent、工作流接口与实时事件 |
| 编排运行时 | 调度器、DAG 引擎、Self-Loop、核查器、工具注册表 | 依赖执行、并发调度、工具调用、回环与验收 |
| 数据与模型 | SQLite、中文 BM25、Mock / DeepSeek | 运行轨迹、证据检索、模型与工具调用 |

### 2.2 领域模型

| 实体 | 说明 |
|---|---|
| Project | 一个研究项目，绑定知识库、团队、工作流 |
| KnowledgeDoc / Chunk | 资料与可检索片段，片段是引用的最小单位 |
| Agent | 角色、模型、温度、系统提示词、工具、插件 |
| Plugin | 能力插件，声明分类、配置与运行时语义 |
| Workflow | 节点与边组成的 DAG，边区分 flow 与 loop |
| Run / NodeRun | 一次运行与每个节点的每次尝试/回环 |
| RunEvent | append-only 调度、分支、工具调用、核查事件 |

### 2.3 节点能力插件

插件不挂在团队上，而是挂在 Agent 节点上。它只负责三件事：

1. **展开**：把一个输入展开成 N 个分支；
2. **约束**：给每个分支不同的视角、证据或温度；
3. **收敛**：内部裁判收敛，或把多个候选暴露给下游/人工。

MVP 已落地的运行时插件 / 工具（14 个）：

**发散思考（`cognition.diverge`）**
在首席分析师节点展开稳健、进取、反方三条分支。每条分支有独立立场与评分，裁判选择主判断，所有候选保留在节点输出中，用户可展开查看。

**引用核验（`verify.citations`）**
抽取报告中的事实性结论，做四态判定（支持 / 部分 / 矛盾 / 无依据），检查引用、数字、方向、单位、统计期间与主体。核查不通过时输出问题清单，触发 Self-Loop；未挂载该插件的核查员按 fail-closed 处理。

**知识检索（`knowledge.retrieve`）**
研究员按角度召回证据，并作为 `knowledge_search` 工具暴露给模型；返回片段、来源与评分。

**数值计算（`tool.calculator`）**
递归下降解析的沙箱算术，只接受数字与四则运算，不走 `eval`。所有派生数字必须经过它，调用写入 `tool.call` / `tool.result` 事件。

工具编排不是另起一套系统：`Agent.tools` 存插件 id，`src/server/tools.ts` 把它映射成工具注册表；Live 模式把同一份 JSON Schema 交给模型的 function calling，Mock 模式直接执行同一个 `invokeTool`，因此离线演示也有真实工具轨迹。

自我批判、任务分解、反方建模、多角色辩论、邻居扩展、时效排序、数值一致性、蕴含判定、数据统计与浏览器抓取都已接入运行时；`tool.python` 是受限统计，不执行任意代码，`browser_fetch` 只读取公开 http(s) 页面。

### 2.4 编排与调度

**DAG 编排。** 节点是非 loop 边的依赖单位；loop 边只用于表达回环，不参与拓扑排序。

**优先级。** 调度器计算每个节点到汇点的最长路径深度，深度越大越优先。三路研究同深度，按画布坐标稳定排序。

**并发。** 默认最大并发 3，三路研究可以并行；分析、写作、核查串行。

**失败处理。** 节点失败最多重试一次；预算超限在模型调用前终止；取消在调度循环边界生效。

**动态性。** 运行时的节点状态、分支、重试、回环都会改变就绪队列；调度器每轮重新计算，而不是一次性静态排程。

### 2.5 Self-Loop 与结果验证

核查器不是“让模型给自己打分”，而是可复现的规则核查。每条主张落到四态之一：`supported` / `partial` / `contradicted` / `unsupported`。

1. 抽取事实性章节中的结论，过滤标题、引用块与列表编号；
2. 从 `[M2]` 这样的标记定位证据；引用不存在直接判无依据；
3. 检查数字：支持区间（`35%—45%` 蕴含 `40%`）与指标锚点（`平均售价 299` 对 `289`）；
4. 检查方向、单位、统计期间与主体：增长被判成下滑、美元对人民币、2024 对 2027、Meta 对苹果，都是矛盾而不是“支持度低”；
5. 计算语义覆盖率，汇总时 `supported` 记 1、`partial` 记 0.5、其余记 0，低于阈值输出问题清单。

可复现基线：42 条手标难例四态准确率 **88%**，`supported` F1 **100%**，11 条矛盾主张 0 条被放过；143 条构造用例四态准确率 **100%**。旧规则在 42 条难例上只有 55%，会把方向相反的主张判成支持。详见 [verification.md](./verification.md)。

核查器不只输出分数，还会给每个问题打上类型和目标节点：

| 问题类型 | 目标节点 |
|---|---|
| 缺引用 / 引用不存在 | 对应角度的研究员（市场 / 产业链 / 竞争） |
| 数字与证据不一致 | 首席分析师 |
| 语义重叠不足 / 逻辑跳跃 | 首席分析师 |
| 表述问题 | 报告撰写师 |

回环流程：

1. verifier 不通过，当前 NodeRun 标记为 waiting，保存核查结果；
2. 按问题优先级选择 target，重置 target 及其下游节点，而不是一律回到 writer；
3. feedback 设为带目标标记的问题清单；
4. loopCount + 1，写入 loop.triggered 事件；
5. target 节点读取 feedback 重跑，下游节点按依赖重新执行；
6. verifier 再核查，直到通过或达到最大回环次数。

例如首轮同时出现“数字不一致”和“缺引用”，系统优先选择 citation，把问题路由到竞争情报员；竞争情报员、首席分析师、撰写师、核查员依次重跑，第二轮核查通过。

达到最大回环次数后，即使未通过也继续终稿，但保留低分并标记“需要人工复核”。这避免了“无限重试”与“假装通过”两个极端。

### 2.6 知识库与引用

- Markdown / TXT 直接入库；PDF 用 `unpdf` 按页抽取，保留页码标记，扫描件拒绝入库；
- 文档记录来源链接、类型（论文 / 报告 / 报道 / 公告）与发布时间；
- 按 `##` 章节切分，单节超过 340 字按句切到约 300 字；
- SQLite 存储片段，检索时在内存计算 BM25；
- 中文使用 `Intl.Segmenter` 词级分词 + 双字回退，兼容英文/数字；
- 研究员按市场/产业链/竞争三个角度检索目标文档，生成 M/L/C 前缀的稳定引用；
- 报告中的引用可点击查看原文片段。

### 2.7 交互与可观察性

- **首页**：项目、团队、最近运行、关键指标、一键开跑。
- **知识库**：MD / TXT / PDF 入库、检索测试、片段与来源查看。
- **Agent 团队**：14 个角色、插件库、节点级插件开关；14 个插件都有运行时。
- **编排画布**：拖动/连线/删除节点，插入专家节点，拖拽运行时插件，查看配置与运行前检查。
- **运行页**：实时图谱、节点轨迹、调度事件、`tool.call` / `tool.result`、报告、证据账本、核查与回环。
- **证据账本**：逐条主张、引用原文、四态标签、核查结论与路由目标。
- **评测**：运行历史、回环前后对比、质量/成本指标。
- **训练**：固定评测集、5 个提示词候选、版本启用与回滚。

### 2.8 技术栈与部署

| 层 | 技术 |
|---|---|
| 前端 | React 19、Vite、React Flow、React Markdown |
| 后端 | Node.js 24、Fastify、SSE |
| 存储 | SQLite（`node:sqlite`） |
| 检索 | 自研中文 BM25 |
| 模型 | Mock / DeepSeek OpenAI-compatible |
| 运行 | 本地单机，默认只监听 127.0.0.1 |

部署只需要 Node.js 22.19+ 与 pnpm：`pnpm build && pnpm start`。

### 2.9 与同类产品的差异

| 维度 | LobeHub | DeepSeek Harness | 织序 AgentLoom |
|---|---|---|---|
| 核心抽象 | 助手/插件市场 | 插件化 Harness | 节点能力插件 + 可验证团队 |
| 编排 | 以对话/助手为中心 | 代码 Agent 运行时 | 可视化 DAG + 回环 |
| 调度 | 通用任务调度 | 运行时工具调用 | 关键路径优先级 + 并发 + 预算 |
| 工具 | 插件市场 | 工具调用 / MCP | 工具注册表 + function calling + 调用轨迹 |
| 验证 | 以人工反馈为主 | 以工具结果为主 | 四态主张判定 + Self-Loop + 训练回滚 |
| 差异点 | 生态与助手 | 工程化运行时 | 认知插件 + 工具运行时 + 验收闭环 |

我们不试图替代它们，而是补上“团队级编排 + 节点级认知 + 结果级验收”这一层。

## 三、应用成效

### 3.1 验证场景

**任务**：生成一份面向投资决策的 AI 眼镜产业链研究报告，重点回答市场空间、价值链分配、竞争格局与主要风险。

**知识库**：6 篇模拟整理资料，35 个片段，覆盖市场、产业链、竞争、技术、风险、投资框架。

**团队**：研究规划师、市场研究员、产业链研究员、竞争情报员、首席分析师、报告撰写师、事实核查员、主编（默认工作流 8 个；团队库共 14 个角色）。

### 3.2 运行过程

1. 输入研究任务，规划师拆出 3 个研究问题；
2. 市场、产业链、竞争三路并行检索（最大并发 3）；
3. 首席分析师展开稳健、进取、反方三条分支；
4. 裁判选择稳健情景作为主判断；
5. 撰写师生成 v1 报告；核查员给出 86%，发现 3 条问题：中国出货量写成 80 万台/35%（证据为 48 万台/21%）、2028 年出货量写成 5000 万台（证据为 3200 万台）、“2027 年第一轮洗牌”缺少引用；
6. Self-Loop：系统按优先级先处理 citation，把问题路由到竞争情报员；其下游的首席分析师、撰写师、核查员随依赖重跑，数字矛盾在同一轮被修正，缺失的引用也被补上；
7. 核查员第二轮 100% 通过，主编终稿。

### 3.3 结果数据

| 指标 | 第一轮 | 第二轮 |
|---|---|---|
| 核查分 | 86% | 100% |
| 问题数 | 3 | 0 |
| 核查结论数 | 18 | 18 |
| 回环次数 | — | 1 |
| 运行耗时（Mock） | — | 约 3–4 秒 |
| Tokens（Mock 计量） | — | 约 32k |
| 工具调用 | calculator 1 次 | calculator 1 次 |

> 说明：以上为 Mock 演示模式的真实运行记录，Token 与耗时为模拟口径；Live 模式的成本与延迟需在接入 DeepSeek 后重新测量。

### 3.4 应用价值

**对研究者**：把“找资料、做分析、写报告、查引用”串成一条可复盘的生产线，减少重复劳动。

**对团队负责人**：能看到每个节点的输出、证据与核查问题，知道报告哪里不可信，而不是只看一个最终文档。

**对平台开发者**：新增一个能力，不需要改整个流程；把插件挂到节点上即可。

### 3.5 可移植性

平台的插件与行业解耦：

- 发散插件不关心“AI 眼镜”还是“储能”，它只负责展开视角；
- 核查插件不关心报告主题，它只负责结论与证据对齐；
- 换行业时替换 Agent 角色、知识库与提示词，运行时不变；检索角度与默认回环路由目前仍是配置代码，下一版抽成 domain pack。

下一步将用“软件交付”或“客服工单”做第二个团队，验证同一套插件与工具的迁移成本。

## 四、商业模式

### 4.1 目标客户

1. **高校与科研机构**：研究团队、智库、实验室，需要可复现的研究流程。
2. **券商、咨询、投资机构**：产业研究、尽调、投委会材料，对引用与核查敏感。
3. **企业战略/市场部门**：竞品分析、政策研究、年度规划。
4. **AI 平台团队**：希望把 Agent 能力封装成内部可复用的团队模板。

### 4.2 价值主张

- 把“一个人写报告”变成“一条可验收的生产线”；
- 把“Agent 黑盒”变成“可观察、可干预的节点”；
- 把“提示词复用”变成“团队模板 + 能力插件复用”。

### 4.3 收入模式

| 模式 | 内容 | 假设价格 |
|---|---|---|
| 私有化部署 | 本地部署 + 知识库 + 团队模板 | 8–20 万元/年 |
| 团队模板订阅 | 行业模板、插件、评测集 | 1–3 万元/年 |
| 实施与陪跑 | 知识库治理、流程定制、培训 | 5–10 万元/项目 |
| 插件分成 | 第三方插件/模板上架 | 平台抽成 20%–30% |

### 4.4 市场测算（假设）

> 以下为早期测算假设，需在试点中校验，不作为对外承诺。

- 目标早期客户：1000 家（高校研究团队 + 中小型券商/咨询/企业战略部）。
- 客单价假设：10 万元/年。
- SAM 假设：1000 × 10 万 = 1 亿元/年。
- 3 年 SOM 假设：30 家付费 × 10 万 = 300 万元/年。
- 成本结构：研发、实施、算力、渠道；MVP 阶段以项目制交付为主。

### 4.5 推广路径

1. **校内试点**：以本校研究团队/创新创业学院为第一个场景，积累运行数据与案例。
2. **行业 PoC**：选择 1–2 个投研/咨询客户，做 4–6 周付费验证。
3. **模板化**：把投研、政策研究、竞品分析做成标准团队模板。
4. **渠道**：与高校实验室、咨询公司、AI 服务商合作分成。
5. **生态**：开放插件契约，让第三方开发者贡献“认知插件”和行业模板。

### 4.6 竞争壁垒

- **协议壁垒**：节点能力插件的契约与运行时语义，不是简单 prompt 模板。
- **数据壁垒**：每个团队模板附带评测集与核查规则，越用越准。
- **迁移成本**：团队模板、知识库、插件组合形成工作区资产。
- **先发场景**：在“可验证投研”这个细分场景建立案例与口碑。

## 附录 B：关键指标口径

- **核查分**：被证据支持的结论数 / 核查结论总数。
- **一次通过率**：首次核查即达到阈值的运行占比。
- **回环次数**：verifier 节点 `iteration` 的最大值。
- **Token**：Mock 模式为模拟计量；Live 模式取模型返回的 usage。
- **耗时**：从 run.started 到 run.completed。

## 附录 C：风险与应对

| 风险 | 应对 |
|---|---|
| 多分支成本高 | 只在关键节点挂载；设置预算与最大分支数 |
| 裁判不可靠 | 规则核查 + 人工复核；保留候选与理由 |

| 演示翻车 | Mock 兜底；提前录屏；准备离线数据 |
| 原创性质疑 | 运行时、调度器、核查器自研；DSH 仅作为思想参考 |
