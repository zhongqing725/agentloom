## 可验证的多 Agent 团队编排、调度与验证平台

> 赛题一：Agent 编排创新应用 · 2026 第五届“未来杯”创新大赛
> 版本 v2.0 · 2026-11-11 · 队伍：【待填】

## 摘要

多 Agent 平台已经不缺“角色”和“连线”，缺的是两样东西：可控的思考方式，和可验证的结果。织序 AgentLoom 把 Agent 节点拆成“角色 + 模型 + 知识源 + 能力插件”，让发散、批判、核查这些认知能力像显卡一样插到任意节点上；再用一条“执行—核查—回环”的闭环，把报告里的每一条结论压回证据原文。

平台的验证不是让模型给自己打分，而是三层确定性规则：第一层做四态判定（支持 / 部分支持 / 矛盾 / 无依据），检查数字、方向、单位、统计期间与主体锚点；第二层把知识库规则编译成三页事实卡，检查报告漏了哪些关键事实、回避了哪些资料分歧；第三层把失败按责任维度路由回上游节点，重跑而不是重试。

在 7 篇资料、40 个片段的 AI 眼镜投研场景里，一次真实运行的第一轮三维结果是“引用 86% / 覆盖 71% / 冲突 0%”，系统把冲突路由回首席分析师，第二轮达到“100% / 100% / 100%”，报告自动补出一段带引用的“口径差异与关键事实补录”。同一套规则在真实模型上也跑通了 3 次，均无越证断言。

本文档按大赛通知的项目白皮书要求组织：项目概述、解决方案、应用成效、商业模式、团队介绍，附录给出 AI 使用说明、指标口径与已知边界。

## 一、项目概述

### 1.1 背景：多 Agent 的三道坎

大模型应用正在从“单轮对话”走向“多智能体协作”。Gartner 预测，到 2028 年约 70% 的 AI 应用会依赖多 Agent 系统（[Gartner，2025-06](https://www.businessworld.in/article/gartner-sees-guardian-agents-capturing-10-15-of-agentic-ai-market-by-2030-559558)）。但真正落地时，团队会连续撞上三道坎。

**第一道坎：编排能力薄弱。** 多数方案是脚本化或硬编码的流水线：角色写死在 prompt 里，流程写死在代码里，改一个环节要动整条链路。可视化画布往往只是“画着好看”，条件分支、循环、子流程、异常回退在运行时并没有真实语义。

**第二道坎：调度策略单一。** 串行执行、广播式通信、固定并发，是开源框架的常态。任务没有优先级，Agent 没有负载与容量概念，失败只会整条重跑。结果是“能跑通”，但谈不上“调度”。

**第三道坎：验证与可信机制缺失。** 这是最容易被忽略、也最致命的一环。Agent 输出的中间结果与最终结论缺乏自动验证，幻觉会沿着协作链传播；所谓“核查”常常是让模型给自己打分，换一轮提示词就换一套标准，分数既不可复现，也不可解释。

织序 AgentLoom 就是围绕这三道坎设计的：把编排变成有运行时语义的图，把调度变成带优先级与负载的队列，把验证变成不依赖模型自评的规则层。

一个具体的失败场景：研究员把“2028 年出货 3200 万台”写进摘要，分析师在综述里引用时记成“5000 万台”，写作阶段又把它当成既定事实展开情景推演。整条链路上没有任何一环发现数字变了，最后报告看起来论证完整，结论却建在一个不存在的数上。这类错误不是靠“换个更强的模型”能解决的，只能靠运行时逐条回查证据。

### 1.2 项目定位

一句话：**把一支 Agent 团队，织成可验证的执行流。**

它不是聊天机器人，也不是“多角色 prompt 拼接”。平台的抽象是节点：

```text
Agent 节点 = 角色 + 模型 + 知识源 + 能力插件
```

插件不绑定某个 Agent。`cognition.diverge` 插到投研 Agent 上会展开投资情景，插到写作 Agent 上会展开叙事结构；`verify.coverage` 插到核查员上才会启用覆盖与冲突检查，拔掉就退回只查引用。**插件管思考方式，Agent 管领域知识**——这是“可复用”的真正含义。

平台也不试图替代 LobeHub、DeepSeek Harness 这类通用 Harness，而是补上它们通常不深做的一层：团队级编排之上的“结果级验收”。

### 1.3 应用范围

首个验证场景是**产业投研**：上传行业资料，多路研究并行，产出带引用的研究报告，再由核查员逐条验收。选这个场景，是因为它同时具备三个特征：资料密集、结论必须可追溯、错误代价高。

平台本身与行业解耦。换行业时替换三样东西即可：Agent 角色与提示词、知识库、评测集；编排画布、调度器、验证规则与回放机制不变。第二、第三场景（软件交付、客服工单、政策研究）在路线图中，验证的是同一套插件与工具的迁移成本。

### 1.4 核心优势

**优势一：验证是一等公民，而且不靠模型自评。** 四态判定 + 锚点检查 + 覆盖/冲突三层，全部是确定性规则；同一份报告、同一份知识库，任何人复跑都得到同样的判定。

**优势二：插件化到节点。** 14 个插件都有服务端运行时，且可以按节点挂载/卸载；关掉插件，行为当场退化，这是可现场验证的 A/B。

**优势三：全链路闭环，而不是单点能力。** 编排、调度、工具、验证、回环、回放串成一条链路：验证失败会改变执行路径（回哪个节点、带什么反馈），而不是只打一个分。

**优势四：可复现。** Mock 模式无需 API Key 即可完整跑通，Live 模式用真实模型；两者共用同一套核查规则，演示、评测、答辩用的是同一份代码。

## 二、解决方案

### 2.1 总体架构

平台分四层，自上而下：

```text
┌────────────────────────────────────────────────────────────┐
│ Web 控制台                                                  │
│ 首页 / 知识库 / Agent 团队 / 编排 / 运行 / 评测 / 插件 / 训练 │
└───────────────────────────┬────────────────────────────────┘
                            │ REST + SSE
┌───────────────────────────▼────────────────────────────────┐
│ Fastify API                                                 │
│ /api/runs  /api/agents  /api/workflow  /api/kb  /api/wiki   │
└───────────────────────────┬────────────────────────────────┘
                            │
┌───────────────────────────▼────────────────────────────────┐
│ 编排运行时                                                   │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌───────────────┐  │
│  │ 调度器    │ │ DAG 引擎 │ │ Self-Loop│ │ 验证器         │  │
│  │ 优先级/并发│ │ 依赖/分支│ │ 路由/回写│ │ 四态+覆盖+冲突 │  │
│  └──────────┘ └──────────┘ └──────────┘ └───────────────┘  │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌───────────────┐  │
│  │ Agent 节点│ │ 插件运行时│ │ 工具注册表│ │ 事件总线/SSE  │  │
│  └──────────┘ └──────────┘ └──────────┘ └───────────────┘  │
└──────────┬─────────────────────────────┬───────────────────┘
           │                             │
     ┌─────▼──────┐               ┌──────▼─────────┐
     │ SQLite      │               │ 模型网关       │
     │ 文档/片段   │               │ Mock / DeepSeek│
     │ 运行/事件   │               │ OpenAI 兼容    │
     └────────────┘               └────────────────┘
```

设计上刻意保持“单进程 + SQLite”：比赛演示、评审复现、VPS 部署都只需要一个 Node 进程；分布式调度、多租户、插件市场明确不在本届 MVP 范围内。

### 2.2 领域模型

| 实体 | 作用 | 关键字段 |
|---|---|---|
| Project | 一个工作区 | 名称、场景 |
| KnowledgeDoc → Chunk | 知识库与检索片段 | 来源、标签、页码、向量 |
| Agent | 可被节点引用的角色 | 角色、模型、温度、提示词、工具、插件、容量 |
| Plugin | 节点能力定义 | 类别、图标、配置 |
| Workflow | 一张可执行图 | 节点、边、调度设置 |
| Run / NodeRun | 一次运行 / 一次节点尝试 | 模式、迭代号、成本、分数 |
| RunEvent | append-only 事件流 | 类型、节点、数据 |

节点分四类：`input`、`agent`、`verifier`、`output`；边分 `flow` 与 `loop`，后者只用于表达回环，不参与依赖计算，避免 DAG 成环。

### 2.3 Agent 团队定义

团队库内置 14 个角色：研究规划师、市场研究员、产业链研究员、竞争情报员、首席分析师、报告撰写师、事实核查员、主编，以及风险审查、估值、数据工程等专家。默认工作流只用其中 8 个，其余角色可以在画布上按需插入。

每个 Agent 可配置：模型、温度、系统提示词、工具集、插件集、并发容量。三条工程能力值得单说：

- **提示词版本化**：训练产生的候选提示词写入 `agent_versions`，可一键启用或回滚；评测集冻结上游上下文，只替换系统提示词，保证两次打分可比。
- **短期记忆**：节点完成后把摘要写入 SQLite `agent_memory`，下一轮按任务关键词召回最近 3 条注入 Live prompt；可查看、手写、清空。
- **按需专家**：画布上“添加 Agent”会同时创建角色与节点，插入后自动接到下游，不需要改代码。

### 2.4 工作流编排

画布基于 React Flow，支持拖动、连线、删除、插入专家、把插件卡拖到节点上。控制结构在运行时都有真实语义：

| 结构 | 实现 | 运行语义 |
|---|---|---|
| 顺序 | DAG 依赖 | 所有非 loop 入边完成后进入就绪队列 |
| 并行 | `maxConcurrency` | 三路研究可同时执行 |
| 条件 | `condition` 节点 | 读取上游输出路径，`gte/lte/eq` 判定，只走命中的出边，未命中节点标 `skipped` |
| 循环 | Self-Loop + loop 边 | 验证失败重置目标及下游，带反馈重跑 |
| 子流程 | `subflow` 节点 | 引用另一张 workflow，执行独立 child Run，最多 2 层 |

边界也写清楚：条件节点目前只支持单条件与 true/false 两路，不支持 `and/or` 组合表达式与嵌套条件；子流程模板通过 seed/API 配置，暂无模板编辑器。这些在答辩时会主动说明，不假装是完整实现。

### 2.5 动态调度

调度器不是“按拓扑序遍历”，而是每个 tick 重新计算就绪队列并排序：

```text
就绪条件：status = pending 且所有非 loop 入边的源节点 = completed
优先级：  depth(node) = 1 + max(depth(下游))   // 到汇点的最长路径
排序：    depth 降序 → Agent 当前负载升序 → 画布 x 升序
```

同一深度按画布 x 排序，保证行为可复现；Agent 有 `capacity`，容量满时节点等待，`node.queued` 事件里能看到 `agentLoad` / `agentCapacity`。失败最多重试 1 次；预算超限时在模型调用前终止，而不是事后记账。

边界：单进程调度，没有抢占、迁移与跨机分发；压力测试证明的是调度链路与并发控制，不是分布式能力。

### 2.6 工具与外部系统

工具注册表统一了三条接入路径：

- **Function Calling**：`calculator`（递归下降解析，只接受数字与四则运算，不走 `eval`）、`knowledge_search`（BM25 + 向量混合）、`data_stats`（受限统计）、`browser_fetch`（公开 http(s) 页面，拦截内网地址，8 秒超时）。Live 模式走 OpenAI `tools` 协议，最多 3 跳；Mock 模式照样执行真工具。
- **MCP**：内置 stdio 客户端，支持 `initialize` / `tools/list` / `tools/call`，通过 `AGENTLOOM_MCP_SERVERS` 配置外部服务。需要说明：默认不启动，演示中未启用；协议是子集，不含 resources / prompts / sampling。
- **A2A**：`/.well-known/agent.json` 暴露 Agent Card，`POST /a2a` 支持 `message/send`、`tasks/get`、`tasks/cancel`，可被其他 Agent 发现并委派任务；是兼容子集，不含 streaming / push。

每一次工具调用都写入 `tool.call` / `tool.result` 事件，运行页与节点输出都可回放。工具错误只进事件流，不终止运行。

### 2.7 结果验证：三层规则

这是平台的核心，也是与“模型自评”划清界限的地方。

**第一层：四态判定。** 抽取事实性章节中的结论，过滤标题、引用块与列表编号；从 `[M2]` 这类标记定位证据；每条主张落到四态之一：

- `supported`：引文能直接坐实；
- `partial`：报告显式声明这是证据缺口、情景假设或待验证，并写清缺什么；
- `unsupported`：以确定语气断言，却无引用或引文不支持；
- `contradicted`：与引文冲突。

判定时检查数字区间（`35%—45%` 蕴含 `40%`）、指标锚点（平均售价 299 对 289）、方向、单位、统计期间与主体。方向相反、币种不同、年份错位、主体错配，都判为矛盾而不是“支持度低”。

**第二层：覆盖与冲突。** 知识库在每次运行前被规则编译成三页事实卡（市场 / 产业链 / 竞争）：指标 + 主体 + 数值 + 年份 + 原文句 + 来源文档。编译不调模型、不落库，40 个片段毫秒级完成。

四态判定的典型例子：

| 报告主张 | 证据 | 判定 | 原因 |
|---|---|---|---|
| 2028 年出货量 3200 万台 | IDC 预计 2028 年达到 3200 万台 | supported | 数字与主体都能对上 |
| 2028 年出货量 5000 万台 [M2] | M2 原文为 3200 万台 | contradicted | 所引证据给的是另一个值 |
| 行业将在 2027 年洗牌 | 报告未给引用 | unsupported | 确定语气断言但无证据 |
| 若渠道补贴延续，2028 年可能超预期 | 报告已声明这是情景假设 | partial | 缺口被显式说明，不计入分母 |

- **覆盖检查**：每页取 Top-3 关键指标（出货量、渗透率、毛利率、份额、BOM、退货率等），检查报告是否出现；漏掉的关键事实回写作补录。
- **冲突登记**：同一指标、主体、单位、年份出现不同数值，且离散度 ≥ 1.1，且句子不是“假设 / 情景 / 乐观 / 保守”时，登记为资料分歧；报告必须说明口径差异，否则回分析师。
- 规则细节包括：指标匹配以分句为边界，跨分句继承指标要求单位兼容；“2028 年达到 3200 万台”会继承前一分句的“出货量”，但不会把万台继承给“渗透率”；不同环节的毛利率、不同公司的份额按主体分组，不互相冲突。

**第三层：回写与路由。** 验证不通过时，不是简单重试，而是按问题类型和责任维度选择目标节点，重置目标及其下游，带反馈重跑。

可复现基线：42 条手标难例四态准确率 88%，`supported` F1 100%，11 条矛盾主张 0 条被放过；143 条构造用例四态准确率 100%。旧规则在 42 条难例上只有 55%，会把方向相反的主张判成支持。

### 2.8 Self-Loop 与反馈优化

回环的路由规则如下：

| 问题类型 | 目标节点 |
|---|---|
| 缺引用 / 引用不存在 | 对应角度的研究员（市场 / 产业链 / 竞争） |
| 数字与证据不一致 | 首席分析师 |
| 语义重叠不足 / 逻辑跳跃 | 首席分析师 |
| 报告漏掉事实卡上的关键事实 | 报告撰写师 |
| 资料存在分歧但报告未说明口径 | 首席分析师 |
| 表述问题 | 报告撰写师 |

关键在“按失败维度路由”：三维中哪一维没过线，就优先选择该维对应的路由；例如冲突维度为 0% 时，即使引用问题更“响”，也会先把冲突交给分析师。重置分析师会连带重置下游写作，因此一轮回环可以同时修掉覆盖与冲突。

第二轮的写作不是简单重写：它会根据事实卡自动补一段“口径差异与关键事实补录”，每条带 `[M…]` 或新铸的 `[W…]` 引用。补录句直接引用原文整句，避免“语义重叠不足”的误判。

反馈优化还有一条训练线：固定评测集 + 5 个提示词候选，用同一套核查器打分，胜出候选写入版本表，可启用或回滚。边界：目前只覆盖撰写师与主编的少量用例，工具选择尚不会自适应。

### 2.9 可观察与回放

- `run_events` 是 append-only：`run.started`、`node.queued`、`node.started`、`node.branch`、`node.merge`、`tool.call`、`tool.result`、`node.completed`、`node.retry`、`verify.failed`、`loop.triggered`、`run.completed`。
- SSE 连接晚到会先回放历史事件，再推送实时事件；运行可以暂停/继续，每个节点完成写 checkpoint。
- 运行详情保留执行图谱、报告、证据账本、核查与回环、事件流五个视图；每次尝试与回环都有一条 `node_runs`，用 `iteration` 区分。

边界：有 checkpoint 记录，但没有回滚到任意 checkpoint 的恢复执行；没有断点续跑。

### 2.10 技术选型与部署

| 层 | 选择 | 理由 |
|---|---|---|
| 前端 | React 19 + Vite + React Flow | 画布与实时状态需要细粒度控制 |
| 后端 | Fastify + SSE | 单进程、低开销，事件流天然适配运行监控 |
| 存储 | SQLite（`node:sqlite`） | 零运维，评审可一键复现 |
| 检索 | 自研中文 BM25 + 哈希向量 | 中文分词与引用编号必须可控，不依赖外部服务 |
| 模型 | Mock / DeepSeek OpenAI 兼容 | Mock 保证离线可复现，Live 证明真实可用 |

部署只需要 Node.js 22.19+ 与 pnpm：`pnpm build && node scripts/build-server.mjs` 产出单文件 `server.mjs`，连同 `dist/` 打成 tar，解到服务器后由 systemd 常驻。公开演示实例跑在 Mock 模式，评委无需 Key 即可复现。

没有选择 LangChain 之类的框架作为底座，是因为本赛题考察的是调度、验证与回环的自定义实现；套用默认示例无法体现这些差异。平台自研了调度器、四态核查器、事实卡编译器与回环路由，框架只出现在模型调用与 HTTP 层。

### 2.11 安全与边界

- 默认只监听本地；公网实例只开 80 端口，数据库不对外。
- `calculator` 不走 `eval`；`browser_fetch` 拦截 localhost 与内网地址；没有任意代码执行。
- API Key 只存在进程内或服务器 `.env`，不写入数据库。
- 没有认证与多租户；这是参赛原型，不是生产系统。
- 演示数据标注为“模拟整理”，不构成真实投资依据。

### 2.12 关键设计取舍

平台里有四个刻意的“不做”，每个都对应一次权衡。

**取舍一：验证用规则，不用模型自评。** 模型自评的优点是能理解复杂语义，缺点是标准随提示词漂移、不可复现。我们选择规则优先：四态判定、锚点检查、事实卡编译全部确定性；Live 模式下模型只负责贴标签，分数由调用方计算。代价是定性结论覆盖有限，收益是同一份报告任何人复跑都得到同样判定。

**取舍二：知识库编译放运行时，不建持久表。** 事实卡每次运行前从 `chunks` 现算，不写新表、不加后台任务。代价是 O(chunks) 的重复计算，收益是没有迁移、没有缓存失效、Vercel 这类无常驻进程的环境也能跑。40 个片段毫秒级完成，当前规模下这笔账是划算的；涨到数千片段时再加缓存或持久化。

**取舍三：回环只修“失败的那一维”，不做全量重跑。** 按维度路由会把分析师及其下游一起重置，一轮能同时修掉覆盖与冲突；但如果两个维度的责任节点分叉（例如覆盖回写作、冲突回分析师），一轮只能优先一个。我们选择“先修最差的一维，下一轮再修另一维”，因为全量重跑会放大成本与不确定性。

**取舍四：单进程 + SQLite，不做分布式。** 评审要能一键复现，部署要能一条命令上线；分布式调度会引入注册中心、消息队列与一致性成本，与“可复现”冲突。代价是并发上限受单机限制，压力测试也只能证明链路正确，不能证明生产级吞吐。

这四个取舍没有对错，只有场景匹配。它们也是答辩时最容易被追问的地方，所以写在白皮书里，而不是藏起来。

## 三、应用成效

### 3.1 验证场景

**AI 眼镜产业链投研**：7 篇模拟整理资料（市场、产业链、竞争、技术、风险、投资框架，以及一篇故意与主流口径冲突的《券商深度：AI 眼镜的三条分歧》），40 个片段。

选择这个场景的原因：资料里既有可核对的数字（出货量、ASP、BOM、毛利率、份额、退货率），也有真实存在的口径分歧（不同机构对 2028 年出货量与渗透率的预测不同），正好能同时检验引用、覆盖与冲突三层。

### 3.2 一次运行的完整链路

1. 输入研究任务，规划师拆出研究问题；
2. 市场、产业链、竞争三路并行检索（最大并发 3），各带 M / L / C 前缀的稳定引用；
3. 首席分析师展开稳健、进取、反方三条分支，裁判按证据覆盖与可检验性收敛；
4. 撰写师生成 v1 报告；
5. 核查员给出 `引用 86% / 覆盖 71% / 冲突 0%`，共 9 条问题：
   - 3 条引用/数字：中国出货量写成 80 万台 / 35%（证据为 48 万台 / 21%）；2028 年出货量写成 5000 万台（所引证据为 3200 万台）；“2027 年第一轮洗牌”缺少引用；
   - 2 条覆盖缺口：漏掉渗透率 3.5% 与 SoC 12.8 亿美元两条关键事实；
   - 4 条冲突未说明：2028 出货量 3200 vs 5000 万台、复合增速 65% vs 85%、退货率 15% vs 12%、Meta 份额 62% vs 55%。
6. Self-Loop：冲突维度最差，路由到首席分析师；其下游撰写师、核查员随依赖重跑；
7. 第二轮 `100% / 100% / 100%`，0 条问题，综合分 100%，主编终稿。报告多出一段“口径差异与关键事实补录”，冲突双方的数值与来源都在。

**必须承认的缺口**：目前没有做“串行 / 单 Agent / 仅引用核验”的对照实验，因此无法给出“相比基线提升了多少”的量化结论。这是决赛前要补的实验，白皮书不把 Mock 的 100% 说成模型准确率。

### 3.6 可移植性

插件与行业解耦：发散插件不关心主题，只负责展开视角；核查插件不关心报告主题，只负责结论与证据对齐；事实卡编译器不关心领域，只按指标语言抽取。换行业时替换角色、知识库与提示词即可。

边界：检索角度与默认回环路由目前仍是配置代码，下一版抽成 domain pack；第二、第三场景尚未落地。

举一个具体的迁移例子：切到“软件交付”场景时，投研的三个检索角度换成“需求 / 架构 / 测试”，事实卡的指标词典换成“响应时间 / 缺陷率 / 覆盖率 / 回滚耗时”，核查规则与回环路由保持不变；需要重写的只有角色提示词与评测集，编排画布和调度器无需改动。

### 3.7 两次失败与修正

**失败一：让模型自己打分。** 早期 Live 核查让模型直接输出总分，结果每轮重写后模型换一套标准，分数长期卡在 0.82，既追不上阈值，也无法解释为什么。修正：核查员只贴标签与理由，分数由调用方按“被引用坐实的主张 / 真正断言的主张”计算，显式声明为缺口的主张不计入分母。修正后三次 Live 运行均达到 1.0，且没有一条越证断言。

**失败二：补录句被判“语义重叠不足”。** 第 2 轮自动补录最初写成“指标：数值 [W1]。”这种短句，规则核查器认为它与原文整句的语义重叠不足，产生 4 条误报——三维已经全绿，问题列表却还挂着 4 条。修正：补录直接引用原文整句，再追加“两家口径存在差异”与引用编号；同一份知识库重跑，第 2 轮问题数从 4 降到 0。

把这两次失败写进来，是因为它们比成功更能说明验证层的设计：规则要的是可复现，任何“聪明”的措辞都可能被规则判错；而规则的误报必须能被定位、被修正，而不是靠调阈值糊过去。

## 四、商业模式

### 4.1 目标客户

1. **高校与科研机构**：研究团队、智库、实验室，需要可复现、可复核的研究流程与教学案例。
2. **券商、咨询、投资机构**：产业研究、尽调、投委会材料，对引用与口径敏感，愿意为“可验证”付费。
3. **企业战略与市场部门**：竞品分析、政策研究、年度规划，痛点是资料多、结论难追溯。
4. **AI 平台团队**：希望把 Agent 能力封装成内部可复用的团队模板与插件。

### 4.2 市场空间

多 Agent 编排不是一个狭窄赛道。MarketsandMarkets 估算，全球多 Agent 编排平台市场 2025 年约 14.8 亿美元，2032 年将达到 172.5 亿美元，2026–2032 年复合增速约 42%，亚太约 44%（[MarketsandMarkets](https://www.marketsandmarkets.com/Market-Reports/multi-agent-orchestration-platform-market-88410938.html)）。

需求侧的信号同样明确：Gartner 预测 2028 年 70% 的 AI 应用会依赖多 Agent 系统。国内，中国网络空间研究院《中国互联网发展报告 2026》显示，2025 年中国企业级 AI 智能体市场规模达到 212 亿元（[中国青年报，2026-11](http://news.youth.cn/jsxw/202611/t20261104_16948925.htm)）；艾媒咨询的口径更大，2025 年中国 AI 智能体市场 804 亿元，预计 2030 年 6968 亿元（[艾媒咨询](https://www.iimedia.cn/c1061/113664.html)）。

两组国内数字口径差异较大（企业级 vs 全口径），本白皮书只引用、不合并，避免制造一个不存在的“权威数字”。

对织序而言，真正可服务的不是整个市场，而是其中的“高可信要求”子集：需要把结论写进投委会材料、政策报告或论文的团队。这个子集的规模远小于总市场，但付费意愿更强、替换成本更高。自下而上的估算路径是：目标高校/机构数 × 渗透率 × 年费，其中渗透率与年费在试点前都只能是假设，因此本白皮书不给出“营收预测”，只给出可验证的推导框架。

### 4.3 价值主张与收入模式

对客户的价值不是“又一个 Agent 平台”，而是三件可度量的事：报告可追溯（每条结论回到原文）、口径可解释（资料分歧被显式记录）、流程可复现（同一输入跑出同一结论）。

收入模式按优先级：

1. **私有化部署 + 年度服务**（主力）：面向券商/企业，按团队规模与知识库规模报价；参考区间 8–20 万元/年，属于内部假设，需在试点中校验。
2. **场景模板订阅**：投研、政策研究、竞品分析等团队模板 + 评测集，按年订阅。
3. **培训与联合课题**：面向高校的课程包、实训案例与师资培训。

### 4.4 推广路径与生态

- **校内试点**：以本校研究团队与课程为载体，积累真实使用数据与教学案例。
- **行业 POC**：选 1–2 家券商或咨询机构做 4–6 周的概念验证，用“核查拦截了多少条越证断言”作为验收指标。
- **模板生态**：把团队模板、插件、评测集做成可交换资产；插件契约开放，但运行时与验证规则保持可控。
- **开源边界**：核心运行时与验证规则不开源；插件接口、示例与文档开放，降低接入成本。

### 4.5 竞争壁垒

- **协议壁垒**：节点能力插件的契约与运行时语义（挂载点、展开/收敛、端口），不是 prompt 模板。
- **数据壁垒**：每个场景模板附带评测集与核查规则，越用越准；错误样本会沉淀成回归用例。
- **迁移成本**：团队模板、知识库、插件组合形成工作区资产，换平台的成本随时间上升。
- **先发场景**：“可验证投研”这个细分场景的案例与口碑。

## 附录 A：AI 使用说明

| 环节 | 用了什么 | 实际作用 | 局限 |
|---|---|---|---|
| 研究规划 | LLM（Mock / DeepSeek） | 拆解问题、生成研究计划 | Mock 为模板；Live 依赖模型质量 |
| 检索与证据 | BM25 + 哈希/神经向量 | 召回片段、生成稳定引用编号 | 无 OCR；神经向量需外部 embedding |
| 发散与裁判 | LLM 多视角 + 规则打分 | 生成稳健/进取/反方候选并收敛 | 候选质量受提示词影响 |
| 报告撰写 | LLM | 生成带引用报告；第 2 轮补录口径差异 | 长文可能遗漏，靠覆盖检查兜底 |
| 结果验证 | **规则**（四态 + 锚点 + 覆盖/冲突） | 判定主张是否被证据支持、是否漏事实、是否藏冲突 | 只处理有数字/引用的陈述；定性结论覆盖有限 |
| 工具调用 | Function Calling / MCP / A2A | 计算、检索、抓取、跨 Agent 委派 | MCP/A2A 为子集，默认不启用 |
| 训练与版本 | 规则核查器打分 | 候选提示词对比与回滚 | 用例少，无留出集与显著性检验 |

一句话：**模型负责生成，规则负责判定。** 验证层刻意不使用模型自评，避免“换一轮提示词就换一套标准”。

## 附录 B：指标口径

- **引用支持率**：被引用坐实的主张数 / 真正断言了事实的主张数；显式声明的证据缺口不计入分母；断言数为 0 直接判 0。
- **覆盖率**：报告中出现的关键事实数 / 事实卡要求的关键事实数（每页 Top-3）。
- **冲突处理率**：已说明口径差异的资料分歧数 / 检出的分歧总数；检测到 0 处时记为 100%。
- **综合分**：三维算术平均，仅用于展示；通过与否要求三维分别达到阈值（默认 0.8）。
- **Mock 与 Live**：Mock 的 Token/成本/耗时为模拟计量；Live 为真实调用记录。两者不混用。

## 附录 C：已知边界与风险

1. **没有多 Agent 交叉验证与置信度校准**：同一主张不会由多个 Agent 独立判断后投票；这是赛题点名的能力，也是下一阶段优先补的缺口。
2. **没有基线对照实验**：缺少串行 / 单 Agent / 仅引用核验三组对照，无法给出“提升多少”的量化结论。
3. **调度是单进程**：无抢占、迁移与跨机分发。
4. **条件分支只支持单条件**：无 `and/or`、无嵌套。
5. **A2A / MCP 是子集**：无 streaming/push，MCP 默认关闭，演示未启用。
6. **验证有边界**：规则只处理有数字或引用的陈述；定性结论、隐喻式表述覆盖有限；覆盖/冲突依赖指标词典，换领域要补词典。
7. **数据为模拟整理**：演示知识库不构成真实投资依据；商业模式中的价格区间为内部假设，未经市场验证。
8. **无认证与多租户**：公网实例仅用于演示，不应承载真实业务数据。
