# 3 分钟演示脚本

> 目标：让评委在 30 秒内记住“节点能力插件”，在 2 分钟内看到“发散 → 裁判 → 核查 → 回环”的完整闭环。

## 录制前

1. 重置演示数据：关闭 API，运行 `pnpm reset`，重新 `pnpm dev`（只重建数据库，不会删评测基准）。
2. 浏览器窗口 1440×900，缩放 100%，隐藏书签栏。
3. 先跑一次示例任务，确认核查从 86% 回环到 100%，且事件流里能看到 `tool.call`。
4. 准备一个备用录屏，防止现场网络或模型波动。
5. 若使用 Live 模型，提前在设置中填好 Key；若现场网络不稳，切回 Mock。

## 分镜

### 0:00–0:20 问题

**画面**：首页 hero。

**旁白**：

> 多 Agent 系统看起来很热闹，但真正落地时，团队是写死的，思考是黑盒的，结果是不可验证的。
> 我们想做的，是把 Agent 团队变成一张可编排、可调度、可验收的执行图。

### 0:20–0:40 一句话定位

**画面**：鼠标划过 hero 右侧的 workflow 卡，停在“14 ROLES / ONE FLOW”。

**旁白**：

> 织序 AgentLoom，一个验证优先的多 Agent 编排调度平台。
> 它的核心不是“更多 Agent”，而是“每个节点都可以插上一张能力卡”。

### 0:40–1:05 知识库

**画面**：点击“知识库”，展示 6 篇资料、35 个片段；在检索框输入“2028 年出货量”，点击检索。

**旁白**：

> 团队的事实底座是知识库。每篇资料被切成可检索的片段，报告里的每一个结论都能回到原文。

**画面**：展示检索命中的片段与分数。

### 1:05–1:25 团队与插件

**画面**：点击“Agent 团队”，展示 14 个角色；镜头停在“首席分析师”的“发散思考 + 数值计算”两个标签。

**旁白**：

> 团队库有 14 个角色，默认工作流用了 8 个。真正改变结果的，是挂在节点上的插件与工具。
> 同样是首席分析师，插上“发散思考”，它会展开稳健、进取、反方三条分支；插上“数值计算”，它的派生数字必须经过沙箱计算，而不是心算。

### 1:25–2:10 运行与发散

**画面**：回到首页，点击“运行示例研究”，进入运行页。

**旁白**：

> 三路研究并行：市场、产业链、竞争。调度器按关键路径排序，最多三个节点同时执行。

**画面**：图谱上三个研究员节点变为“执行中”，随后分析师节点展开 `node.branch` 事件。

**旁白**：

> 到了首席分析师，节点展开三条思维分支。每条分支有独立的视角和评分，最后由裁判收敛成一个主判断。
> 这不是把一条思维链复制三份，而是三种不同的认知策略。

**画面**：点击分析师节点，弹窗顶部是“工具调用（calculator → 79.68）”，下面是三张候选卡片与“裁判选择”。

**旁白**：

> 收敛之前，它调用了一次计算器：3200 万台 × 249 美元，得到 79.68 亿美元。参数、结果、耗时都在事件流里，不是 prompt 里写死的数字。

**画面**：切到“事件流”，停在 `tool.call` / `tool.result` 两行。

### 2:10–2:45 核查与回环

**画面**：点击“核查与回环”标签。

**旁白**：

> 报告写完后，事实核查员逐条核对：引用是否存在，数字是否对得上，方向、单位、统计期间是否一致。
> 第一轮 86%，发现三个问题：中国出货量 80 万/35% 与证据 48 万/21% 矛盾；2028 出货量 5000 万缺证据；2027 洗牌缺引用。

**画面**：切到“执行图谱”，展示 `verify.failed` 与 `loop.triggered` 事件；竞争情报员、首席分析师、写作节点依次出现 L2。

**旁白**：

> 系统没有重试，而是按优先级先处理缺引用，回竞争情报员；分析师和撰写师作为下游一起重跑，数字矛盾在同一轮修正。第二轮核查 100% 通过。注意，四态判定不会把方向相反的主张判成“支持”。

### 2:45–3:00 收尾

**画面**：切到“研究报告”，展示带 `[M2]` 引用的终稿；再切到“评测”，展示回环前后对比。

**旁白**：

> 一条可观察、可干预、可验证的研究生产线。
> 织序 AgentLoom：让 Agent 团队的能力，像插件一样可插拔；让每一个结论，都有证据。

## 30 秒电梯版

> 多 Agent 平台不缺角色，缺的是“可控的思考”和“可验证的结果”。
> 织序把能力做成插件与工具，插到任意 Agent 节点上：插上发散卡，一个节点展开三种视角；插上计算器，派生数字必须经过沙箱；插上核验卡，结论必须通过证据检查；不通过就按问题类型路由回上游重跑。
> 我们用一个 AI 眼镜投研场景，跑通了知识库、编排、调度、发散、核查、回环的完整闭环。

## 现场可能被问到的问题

**Q：这和 Dify / n8n 有什么区别？**
A：它们编排“流程”和“工具节点”；我们编排的是“节点的认知方式”，同时把工具执行收进同一个节点运行时——`calculator`、`knowledge_search` 都在事件流里。再加上核查驱动的回环，而不是失败重试。

**Q：工具编排具体在哪？**
A：`Agent.tools` 映射到工具注册表；Live 模式走 OpenAI `tools` 协议，Mock 模式直接执行同一个 `invokeTool`。运行页能看到 `tool.call` / `tool.result`，节点输出保留参数、结果、耗时。当前只有两个工具，MCP 是下一阶段。

**Q：三个分支真的比一个好吗？**
A：MVP 用回环前后的核查分证明“验证能提升最终质量”；单分支 vs 三视角的 A/B 是下一阶段的评测重点，已有实验设计。

**Q：85→100 是不是演的？**
A：`pnpm smoke` 用临时库重跑，断言第一轮低于 0.9、至少一次回环、第二轮通过。四态判定有独立基准：42 条手标难例准确率 88%，11 条矛盾主张 0 条被放过。数字可以复跑，不是写死的。

**Q：换个行业还能用吗？**
A：插件与工具不绑定行业，Agent 提供领域知识；换团队换角色、知识库和提示词即可。但当前演示的检索角度与默认回环路由仍是配置代码，多场景 domain pack 是下一版。

**Q：为什么不用现成的 Agent 框架？**
A：我们借了 DSH 的插件化思想，但运行时、调度器、核查器、可视化都是自己实现的；重点在“可验证的节点能力”，不是再做一个聊天壳。
